# 06 · Machine learning

## Scope

| Model | Status | Shipped as |
|---|---|---|
| Unusual-traffic detection v1 (statistical baseline) | **Core** | Heatmap layer + anomaly events |
| Arrival time (ETA) for LOWW, LZIB, LHBP | **Core** | Arrival board + aircraft card |
| Destination: route lookup | **Core** | Aircraft card |
| Destination: kinematic re-ranker | Stretch | Replaces the lookup in the card when it beats it |
| Unusual-traffic detection v2 (STL / Isolation Forest) | Stretch | Replaces v1 when it beats it |

Per-flight "unusual flight" detection is not planned: it needs routes and schedules we don't have.

## Conventions

- Feature code lives in `ml/` and in `libs/airspace_common`; training and serving import the same functions ([04](04-pipelines.md#shared-definitions)).
- Training data is extracted from Postgres to Parquet with DuckDB, then trained with scikit-learn / LightGBM.
- **MLflow** (private, [01](01-architecture.md#hosting)):
  - Experiments: `anomaly`, `eta`, `destination`.
  - Every run logs the git SHA, data window, feature list, metrics, baseline metrics and the model artifact.
  - Registered models use the aliases `champion` (served) and `challenger`.
  - A challenger is promoted only if it beats the champion on the same hold-out window by the model's promotion metric.
  - Serving loads `models:/<name>@champion` at start and every 10 min.
- **Public results:** every training run writes a row to `ops.model_runs`; Grafana's public *Models* dashboard reads it. Each model has `ml/<model>/MODEL_CARD.md` (intended use, data window, metrics vs baselines, known failure modes). MLflow itself is never public.

## 1 · Unusual-traffic (anomaly) detection

**Question:** is the traffic in this hexagon unusually high or low for this hour of the week?

- **Unit:** (`h3_r4` cell, 15-min bucket). H3 resolution 4 cells average ~1,770 km².
- **Signal:** `density = n_obs / n_global_snapshots` from `agg.traffic_h3_15m` and `agg.coverage_15m`.
- **Baseline (`baseline_recompute`, daily):** for each cell and hour of week, the median and MAD of density over the 28 days before today (up to 4 buckets × 4 weeks = 16 values), and `n_weeks`.
- **Scoring (`anomaly_scoring`):**
  - If `n_weeks ≥ 3` for the cell and hour of week: `baseline_kind = hour_of_week`, using that median and MAD.
  - Otherwise `baseline_kind = cold_start`: median and MAD of the same hour of day over the last 7 days, split weekday/weekend. The UI shows "baseline warming up".
  - `robust_z = (observed − median) / (1.4826 · MAD + 0.05)`.
  - Flag, persistence, clustering and event rules: [04](04-pipelines.md#anomaly_scoring).
- **Known limits:**
  - A receiver going offline in OpenSky's network looks like a real traffic drop. `low` cells and events are labelled "may be a receiver coverage gap".
  - There is no ground truth.
- **Evaluation:**
  - Inject synthetic anomalies (±30–80% density in random cells for 1–3 hours) into a hold-out week; report precision and recall of *persistent* flags.
  - Report flags per day and anomaly events per day on ordinary weeks.
  - Keep a list of real events (storms, closures, strikes) in the model card as a qualitative check.
- **v2 (stretch):** STL decomposition per cell, or Isolation Forest on (density, avg altitude, share descending, neighbour densities). Promoted only if its synthetic-injection recall is higher at the same events-per-day rate.

## 2 · Arrival time (ETA)

**Question:** when will this inbound flight touch down at LOWW, LZIB or LHBP?

- **Label:** `core.flights.arrived_at` with `arr_source = 'observed'` ([04](04-pipelines.md#flights_sessionizer)). Precision is limited by sampling to roughly ±45–90 s; the model card states it.
- **Training rows:** every snapshot of a labelled flight while it was an *inbound candidate* for its arrival airport (same rule as serving, [04](04-pipelines.md#shared-definitions)). Target = `arrived_at − snapshot_time` in seconds. Candidates that landed elsewhere or never landed have no label and are not used.
- **Features:**

| Group | Features |
|---|---|
| Kinematics | great-circle distance to the airport, ground speed, height above the airport (QNH-corrected, [04](04-pipelines.md#shared-definitions)), vertical rate, difference between track and bearing to the airport |
| Context | hour of day, day of week, arrivals into the same airport in the last 30 min, aircraft within 50 km of the airport |
| Weather | wind component along the active runway (METAR + `ref.runways`; active runway = the runway end most aligned into the wind), visibility, ceiling, flight category |
| Aircraft | wake category from `category`, typecode family |

- **Baselines:**
  - B0: `distance / ground_speed`.
  - B1: the median time-to-touchdown of training rows for the same airport and 25 km distance band.
- **Model:** LightGBM, one quantile model each for p10, p50, p90.
- **Split:** time-based; train on all weeks before the last full week, test on the last full week. Never random (points of one flight would leak).
- **Metrics:**
  - MAE of p50 in minutes, overall and by distance band (0–50, 50–150, 150–400 km).
  - p10–p90 coverage (target 80% ± 5).
  - Improvement over B0 and B1.
- **Promotion metric:** overall p50 MAE.
- **Success:** p50 MAE lower than **B1** on the hold-out ([00](00-overview.md#success-criteria)).

## 3 · Destination

**Question:** where is this airborne flight going?

### Core: route lookup

- `ref.callsign_routes` is rebuilt daily by `routes_refresh` from the last 28 days of `raw.opensky_flights` (rows with a non-null `est_arr_icao`). Callsigns with no OpenSky rows fall back to Zenodo.
- `destination_inference` writes the top 3 destinations by `share` for each active flight with a callsign (`method = 'route_lookup'`). Flights whose callsign is unknown get no prediction.
- **Evaluation:** top-1 and top-3 accuracy on finalized flights with an arrival label (`observed` preferred, else `opensky`), at 10%, 50% and 90% of flight progress (by time between `first_seen` and `last_seen`).
- **Baseline:** the nearest airport (OurAirports `large_airport` or `medium_airport`) within ±30° of the current track.

### Stretch: kinematic re-ranker

- For candidate airports within reach (the route lookup's top 5 plus `large_airport`s within 30° of track and within 1.2 × remaining range for the typecode family), compute bearing difference, distance, altitude trend, lookup probability and whether the airport is a hub of the airline.
- A LightGBM classifier on (snapshot, candidate) pairs, labelled from `core.flights.arr_icao`. Output: top 3 with probabilities (`method = 'reranker'`).
- Shipped only if it beats the route lookup's top-1 accuracy at 50% progress on the hold-out.

Destination predictions are shown in the aircraft card only. They do not decide which flights get an ETA.
