# 06 · Machine learning

All training runs are tracked in **MLflow**:
- Experiments: `anomaly`, `eta`, `destination`.
- Every run logs the git SHA, data window, feature list, metrics and the model artifact.
- Registered models use the aliases `champion` (served) and `challenger`.
- A weekly job trains a challenger and promotes it only if it beats the champion on the same hold-out window.
- Serving code loads `models:/<name>@champion`.

Training data is extracted from Postgres and the Zenodo Parquet files into Parquet with **DuckDB**, then trained in the `ml/` package (scikit-learn, LightGBM).

## 1 · Airspace anomaly detection

**Question:** is the traffic in this hexagon unusual for this hour of the week?

- **Unit:** (`h3_r4` cell, 15-min bucket).
- **Signal:** `density = n_obs / n_global_snapshots` (average airborne aircraft present), from `agg.traffic_h3_15m`.
- **Baseline v1 (statistical):**
  - For each cell and hour of the week: median and MAD of density over the last 4 weeks.
  - `robust_z = (observed − median) / (1.4826 · MAD + ε)`.
  - Flag when |z| ≥ 3 and `max(observed, median) ≥ 2` aircraft, so near-empty cells aren't flagged.
  - Cold start: before 2 weeks of data, use the same hour of day over the last 7 days, split weekday/weekend, and show a "baseline warming up" badge.
- **v2 candidates:** STL decomposition per cell; Isolation Forest on (density, avg altitude, share descending, neighbour densities). Compared against v1 in MLflow.
- **Evaluation (no labels exist):**
  - Inject synthetic anomalies (±30–80% density in random cells over 1–3 hours) into a hold-out week and measure precision/recall.
  - Report the false-positive rate on ordinary weeks.
  - Keep a curated list of real events, such as storms, closures and strikes, as a qualitative check.
- **Coverage mask:** buckets with less than 50% of expected snapshots are never scored.

## 2 · Arrival time (ETA) for LOWW, LZIB, LHBP

**Question:** when will this flight touch down?

- **Label:** `core.flights.arrived_at`, the first `on_ground` point (or the last airborne point below 300 m) within 5 km of the airport. Training rows are snapshots of inbound flights at 400 km → 0 km; target = `arrived_at − snapshot_time` in seconds.
- **Data:** our own collected trajectories (Zenodo has none). Start collecting early: one week ≈ 1,500+ arrivals across the three airports.
- **Features:**

| Group | Features |
|---|---|
| Kinematics | distance to airport (great-circle), ground speed, altitude, vertical rate, difference between track and bearing to the airport |
| Context | hour of day, day of week, arrivals into the same airport in the last 30 min, aircraft within 50 km |
| Weather | wind component along the active runway (from METAR + `ref.runways`), visibility, ceiling, flight category |
| Aircraft | wake category / typecode family, origin region |

- **Baseline:** `distance / ground_speed`.
- **Model:** LightGBM, one quantile model each for p10, p50 and p90.
- **Split:** time-based (train on weeks 1…n−1, test on week n). Never split randomly, because points from the same flight would leak into both sets.
- **Metrics:**
  - MAE of p50 in minutes, by distance bucket (0–50, 50–150, 150–400 km).
  - p10–p90 coverage (target ~80%).
  - Improvement over the baseline.

## 3 · Destination prediction

**Question:** where is this airborne flight going?

- **Stage 1, route prior:** `ref.callsign_routes`, built from Zenodo (2019–2022) blended with our own `core.flights` (weighted towards recent data, because routes change). Gives P(destination | callsign).
- **Stage 2, kinematic re-ranker:**
  - For candidate airports within reach (fuel/range heuristic), compute: bearing difference, distance, altitude trend, prior probability, and whether the airport is a hub of the operator.
  - Train a gradient-boosted classifier on (flight snapshot, candidate) pairs, labelled from `core.flights.arr_icao`.
  - Output the top 3 with probabilities.
- **Baselines:** prior only; nearest airport ahead.
- **Metrics:** top-1 and top-3 accuracy by flight progress (10%, 50%, 90% of the flight).
- **Use:** shown in the aircraft card. It also decides which flights get ETA predictions.

## Model cards

Each registered model has `ml/<model>/MODEL_CARD.md` covering: intended use, data window, metrics vs baseline, known failure modes (e.g. sparse coverage, diversions).
